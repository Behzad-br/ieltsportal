# Database migrations (Alembic)

PostgreSQL (Neon staging / production) schema is owned by **Alembic**.  
Do not rely on `Base.metadata.create_all()` or additive `ALTER TABLE` patches to evolve staging/production.

## Layout

```
backend/
  alembic.ini
  alembic/
    env.py                 # loads DATABASE_URL from app.config.settings
    versions/
      20261012_0001_*.py   # empty baseline (stamp-only)
      20261012_0002_*.py   # expand-only: migration_metadata
```

## Baseline strategy

The Neon database already had tables and data before Alembic existed.

1. Revision `20261012_0001` is an **empty baseline** (no CREATE TABLE).
2. Existing DBs are **stamped**, never replayed:
   ```bash
   cd backend
   alembic stamp 20261012_0001
   alembic upgrade head
   ```
3. Never autogenerate an initial migration that recreates all tables against a populated DB.

## Developer workflow (every model change)

1. Change SQLAlchemy models under `app/*/models.py`.
2. Create a revision:
   ```bash
   cd backend
   alembic revision -m "short_description"
   # or, after careful review only:
   alembic revision --autogenerate -m "short_description"
   ```
3. **Manually review** the generated migration (expand-only preferred; no blind drops).
4. Test against a staging copy / non-prod database:
   ```bash
   alembic upgrade head
   alembic current
   ```
5. Run backend tests.
6. Deploy application **after** migrations:
   ```bash
   alembic upgrade head
   ```

## Never

- Edit production/staging schema by hand in the SQL console (except emergencies + document a follow-up revision).
- Rely on `create_all` to migrate an existing Neon DB.
- Accept an autogenerated migration without reading every op.
- Drop or rename business columns without an explicit approved phase plan.
- Run concurrent `alembic upgrade` from every HTTP worker on boot.

## Environment flags

| Variable | Staging/Production | Development |
|---|---|---|
| `ENVIRONMENT` | `staging` / `production` | `development` |
| `AUTO_CREATE_SCHEMA` | `false` (default when ENVIRONMENT is staging/production) | `true` (default) |
| `REQUIRE_MIGRATIONS_AT_HEAD` | `true` (default in managed envs) | `false` |

Startup with `AUTO_CREATE_SCHEMA=false` verifies required tables and (when required) that Alembic `current == head`. It does **not** run migrations.

## Deployment step

Explicit deployment command (one place, not every request process):

```bash
cd backend
alembic upgrade head
alembic current   # expect head revision
```

Then start uvicorn/PM2.

## Useful commands

```bash
alembic history
alembic current
alembic heads
alembic upgrade head
alembic downgrade -1          # only when the revision is known-safe
python -m app.cli.migrate --alembic
```

## Phase 3 prove-out

`migration_metadata` is an internal marker table created by `20261012_0002`.  
It must not hold business data. Future phases add expand-only domain migrations on top of head.
